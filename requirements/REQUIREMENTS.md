# CRTI technical requirements (draft)

| ID | Requirement | Acceptance test |
|---|---|---|
| 01 | Server-measured active context | Show measured occupancy, limit, scope, timestamp, actual model and effort per supported session. Test stable, effort-only and model-change sessions; label unavailable measurements and never substitute cumulative tokens. |
| 02 | Conversation health | Report persistence, known technical limits and unavailable health signals separately. Inject one known fault and one unknown state; verify correct classification. |
| 03 | Advance warnings | Allow configurable context and allowance thresholds (test at 70%, 85%, 95%). Warn at each crossed threshold while input remains usable; distinguish unpredictable faults. |
| 04 | Context degradation | Log compaction and model-transition events, affected context categories and known/unknown retention. Compare before/after occupancy and verify retained test decisions; do not expose hidden reasoning. |
| 05 | Usage ledger | Reconcile account-window and Goal/task usage with documented units and weights, model/effort, input/output/cache/reasoning where available, and delegated/tool/background activity. Test delayed/missing data; label freshness, unknowns and unexplained residuals. |
| 06 | Forecast | Before substantial work show an estimated usage range, scope, assumptions and uncertainty. Compare actual comparable usage with the forecast; explain deviations and unavailable data. Use a synthetic test interval (e.g. 1,000–2,000 units), test an actual value inside and outside it, and require an explicit deviation explanation for the latter. Test values are not current platform quotas. |
| 07 | Budgets | Allow user-set budget limits and bounded execution. Test a budget stop with a verified checkpoint, visible reset/remaining allowance and authorized resume without repeated completed work. |
| 08 | Checkpoints | Persist decisions, task state and source references in an inspectable checkpoint before predictable exhaustion or a necessary model transition. Verify retrieval and integrity against the recorded state. |
| 09 | Migration | Resume in a successor or after a model transition using a defined set of preserved decisions/constraints and source references; report missing items and avoid full transcript imports. Test completeness against the known reference set. |
| 10 | Recovery | Retrieve readable records from failed conversations. Inject input lock or a retrieval fault; verify recoverable records and explicit unrecoverable gaps. |
| 11 | Export resume | Interrupt a multi-gigabyte download, resume against verified object identity and verify checksum; test changed identity and expired authorization. |
| 12 | Selective export | Export individual chats and projects. Compare the exported message/file inventory to the authoritative selected scope; report omissions and completeness explicitly. |
| 13 | Delta export | Export changes since a recorded checkpoint; compare added, changed and deleted records to the authoritative delta without silent omission. |
| 14 | Integrity | Supply manifest, lengths, schema and checksums; inject missing and altered records and verify that validation detects both. |
| 15 | Diagnostics | Provide actionable error identifiers with affected scope, retry options and correlation time. Test access, capacity and transport failures without conflating causes. |
| 16 | Communication | Publish dated changes, affected scope, known issues and measurable milestones; distinguish announced, staged and deployed status. |
| 17 | Autonomous task continuation and validated completion | Continue an authorized multi-step objective across turns from verified state without redundant continuation prompts. Preserve a visible pending approval, blocked state and authorized resume; test that no completed work repeats and security controls remain intact. A platform-controlled completion gate checks every criterion against fresh authoritative evidence and refuses missing, stale, contradictory or model-only evidence. Test completion, essential input, real blocker, budget exhaustion and explicit approval stops; state the reason. |
| 18 | Tool availability and continuity | Detect assigned-tool loss, classify permission, connection, exposure, dispatch or invocation faults when evidenced, otherwise unknown. Inject transient/permanent failures and perform bounded retries; test access across declared product surfaces without unnecessary reinstallation. |
| 19 | Mandatory tool execution and result validation | Enforce configured mandatory calls and fresh result validation at host level independent of model compliance. Test omitted calls, stale or invalid results and exhausted retries; suppress dependent claims or explicitly report failure, never substitute a result. |
| 20 | Tool execution audit and telemetry | Expose auditable tool/Goal execution metadata: assignment/exposure, actual attempts, outcome, model/effort, timestamps, retry count, error ID, pending approval and scope. Test no invocation versus invocation failure and reconcile sampled events/usage; protect private content. |
| 21 | Library storage, discovery and indexing status | Document a discovery service target and configurable/testable SLA. After acknowledged storage test listing and exact-name retrieval within the SLA; distinguish stored, indexing pending, indexed, indexing failed and inaccessible, including permissions and real cross-surface capability boundaries. In a synthetic test set the discovery SLA to 60 seconds; verify success within the limit or an explicit delayed/failed status at expiry. This is a proposed test configuration, not a claim about the current service SLA. |
| 22 | Stable Library identity and idempotent storage | Return stable retrievable file/version identity upon storage; test direct readback independent of indexing, rename and idempotent retry of the same logical upload. Distinguish intentional copies/versions and prevent accidental duplication. |

All are proposed requirements, not existing functionality. No invented telemetry or guaranteed prediction of arbitrary failures.

Requirements 18–20 extend health, warning, recovery and diagnostics (02, 03, 10, 15); 21–22 extend checkpoints and migration (08, 09). No claim that the controls currently exist. Unknown causes remain unknown.

## Requirement 17 evidence and test

OpenAI's [Using Goals in Codex](https://developers.openai.com/cookbook/examples/codex/using_goals_in_codex) guide (retrieved 2026-11-25) describes Goals as persisted, thread-scoped objectives with lifecycle state and says completion should follow checking concrete evidence. It also describes user/system control of pause, resume, clear and budget-limited transitions. This is official product documentation, not an independent test of host enforcement.

Observed Codex Goals evidence in this execution (2026-11-25): `get_goal` returned the full CRTI objective with status `active` after continuation; an earlier simple Goal in this thread ran `git branch --show-current` and `Test-Path handoff/CODEX_TASK.md` (results `crti-draft` and `True`) and the Goal API returned status `complete` after those checks. This verifies that Goal state and concrete command results were observable in this thread. It does **not** prove that the platform itself rejected a completion attempt with missing or stale evidence, or that every Codex host uses identical enforcement.

Acceptance test for the proposed control: create a Goal with a finite criterion set and recorded evidence references. Pass the completion request only when every criterion has fresh evidence from its declared authoritative surface. Inject (1) one missing criterion, (2) one contradictory result, (3) one stale result and (4) a model-only assertion. In all four negative cases, verify that the platform keeps the Goal non-complete and identifies the exact failed criterion. In the all-pass case, verify the persisted Goal state, objective, evidence references and completion result. Also verify that pausing, resuming and budget exhaustion follow their documented owner/system controls. Log each transition and the source/version used; do not infer enforcement from the model's final prose.

The Codex Goals guide is evidence for the documented design and the live Goal API observations are evidence for this task's state transitions. Neither is proof that the negative completion-validation tests already pass. CRTI-017 and CRTI-019 therefore remain proposed platform requirements.
